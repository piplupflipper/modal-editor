# 段階 1 の検証: 拡張機能への RPC の応答時間

要件定義 8 章の段階 1 は、別のプロセスで動く拡張機能への RPC の応答時間が、キー入力ごとの操作に使える範囲に収まるかを確かめる段階である。
この文書は、その計測の手順、数値、結論と、基本設計 5.4 の期限の既定値の提案を書く（#36）。

## 結論

キー入力の間隔を模して、問い合わせの前に 20 ms か 200 ms の間隔を置き、イベントループが使う経路（`Host.Send`）で測った。
起動済みの拡張機能への `textObject/resolve` の往復は、3 回の計測のどれでも p50 が 0.14〜0.26 ms、p99 が 0.22〜0.37 ms、最大が 0.57 ms 以下だった。
1 万行と 10 万行のバッファで編集の差分を送った直後の往復は、20 ms の間隔を置いて p99 が 0.68 ms 以下、最大が 2.1 ms 以下だった。

この数値から、キー入力ごとの問い合わせを別のプロセスへ送る設計は、このマシンでは応答時間の点で実用になると判断する。
要件定義 8 章が「応答時間が実用にならないと分かった場合」に求める、6 章の「拡張機能の実行方式」の見直しは行わない。

期限の既定値は 100 ms を提案する（仮）。
既定値はオーナーの裁定を待つ項目で、この文書は提案と根拠だけを書く。
100 ms では、およそ 20 万行を超えるバッファを開いた直後に、未起動の拡張機能へ送る最初の問い合わせが失敗する見込みである。
根拠と、この見込みへの対処の案は「期限の既定値の提案」の節に書く。

## 計測したもの

本体の側は `internal/exthost` の `Host` を使い、拡張機能の側は標準の拡張機能 `cmd/modal-editor-ext-line`（行のテキストオブジェクト `il` と `al`）を子プロセスとして起動した。
イベントループ（`internal/editor`）は端末ライブラリの裁定（#9）を待っていて未実装なので、イベントループと画面の描画は計測に含まない。

問い合わせの経路は 2 つある。
`Host.Call` は、呼んだ goroutine が応答まで止まる経路で、テストや計測のコマンド向けである。
`Host.Send` は、待たずに戻り、結果を `Host.Events` のチャネルで渡す経路で、イベントループが使う（`internal/exthost` の `Host.Call` の doc）。
`Send` は結果を待つ goroutine を 1 つ起こすので、`Call` より 1 段多い。

連続で問い合わせると、拡張機能の goroutine、OS のスレッド、CPU が起きたままなので、キー入力の間に数十〜数百 ms 空く場合より往復が短くなる。
そこで、問い合わせの前に間隔を置いた計測を代表値とし、間隔を置かない値は「連続で送ったときの下限」として残す。

| 項目 | 測った区間 | 回数 |
|---|---|---|
| 起動から最初の応答まで | 1 行のバッファを開いた未起動の拡張機能へ `Call` で問い合わせ、子プロセスの起動、`initialize`、`buffer/open` を経て応答が届くまで。回ごとに `Host` を作り直す | 100 |
| 起動済みの往復 | 100 行のバッファで、稼働中の拡張機能への往復。間隔は 0、20 ms、200 ms の 3 通りで、それぞれ `Call` と `Send` の 2 経路を測る。`Send` は `Events` から結果を受け取るまで | 間隔 0 は 10,000、間隔ありは 300 |
| 1 万行と 10 万行、行の中の編集 | `Host.ChangeBuffer` で 1 文字の挿入か削除の差分を送り、直後に新しいバージョン番号で `Call` で問い合わせて応答が届くまで。間隔は 0 と 20 ms | 間隔 0 は 5,000、20 ms は 300 |
| 1 万行と 10 万行、行を足す編集 | 同じく、1 行の挿入か削除の差分を送り、直後の往復まで。行の数が変わるので、本体の写しと拡張機能の複製で、行の配列の編集位置より後ろを動かす | 同上 |
| 1 万行、10 万行、100 万行の開始 | 大きなバッファを開いた未起動の拡張機能へ問い合わせ、起動、全文の送信、最初の応答まで | 1（各計測で 1 回だけ） |

起動済みの往復は、測る前に間隔 0 で 1,000 回を捨て、間隔ごとにも最初の 20 回を捨てた。
編集は、組み合わせごとに最初の 100 回を捨てた。
大きなバッファの 1 行は 40 バイトの ASCII で、10 万行で約 4 MB、100 万行で約 40 MB である。
編集の位置とカーソルはバッファの中央の行に置いた。

p50 と p99 は、測った値を小さい順に並べ、最も近い順位の値（nearest-rank）を取った。
間隔を置いた計測は 300 回なので、p99 は大きい方から 3 番目の値である。

## 環境

| 項目 | 値 |
|---|---|
| 計測した日付と時刻 | 2026-11-16 の 02:21〜02:30（JST） |
| CPU | AMD Ryzen 9 8945HX（16 コア 32 スレッド、最大 5.06 GHz） |
| メモリ | 29 GiB |
| カーネル | Linux 7.0.0-31-generic |
| Go | go1.27.4 linux/amd64、`GOMAXPROCS=32`、`-race` なし |

同じマシンで他の作業が重い処理を走らせている可能性があったので、計測を 3 回繰り返した。
計測の間の負荷として、次の 2 つを各回で記録した。

| 回 | マシン全体の CPU の使用率（3 分間の平均） | テストのプロセスの非自発的なコンテキストスイッチ |
|---|---|---|
| 1 回目 | 2.7% | 17 回 |
| 2 回目 | 2.9% | 17 回 |
| 3 回目 | 4.2% | 41 回 |

CPU の使用率は、計測の前後で読んだ `/proc/stat` の差から求めた、計測の全体（約 3 分）の平均で、計測そのものの CPU 時間を含む。
平均なので、数秒だけ他の処理が CPU を使ったかどうかは、この値からは分からない。
コンテキストスイッチの数は `/proc/self/status` の `nonvoluntary_ctxt_switches` の差で、拡張機能の子プロセスの分は含まない。

## 手順

リポジトリの最上位で次を打つ。
計測のテスト（`internal/exthost` の `TestStage1Latency`）は、`cmd/modal-editor-ext-line` を一時ディレクトリへビルドし、宣言ファイル `manifest.json` と一緒に置いてから起動する。
環境変数 `MODAL_EDITOR_LATENCY` が `1` でないときは読み飛ばすので、`make test` では動かない。
1 回の計測に約 3 分かかる。

```console
$ MODAL_EDITOR_LATENCY=1 go test -run TestStage1Latency -count=1 -timeout 30m -v ./internal/exthost
```

`RESULT` で始まる行が各項目の結果である。
3 回の計測は、この命令を続けて 3 回打った。

### ばらつき

間隔を置いた往復の p50 は、同じ項目の 3 回の差が 2 割程度に収まった。
間隔を 20 ms から 200 ms に延ばすと、p50 は 1.5〜2 倍になり、連続で送った値の 4〜9 倍になった。
原因は確かめていない。
待っている goroutine と OS のスレッドの起床と、CPU の省電力状態からの復帰に時間がかかると推測する。

p99 と最大は、1 回だけの外れ値に左右されるので、回ごとの差が大きい。
1 万行の行の中の編集（間隔 20 ms）の p99 は、2 回目だけ 676 µs で、他の回の 2〜3 倍だった。
10 万行の行を足す編集の最大は、1 回目の間隔 20 ms で 2,058 µs、間隔 0 で 1,398〜1,999 µs だった。
この編集は 1 回ごとに 10 万要素の配列の後ろ半分を動かし、大きな割り当てを伴うので、ガベージコレクションに当たるかどうかで値が揺れると推測する（プロファイルは取っていない）。

`Send` の経路は `Call` より、間隔を置いた p50 で 13〜49 µs 大きかった。
期限の 100 ms に対しては、この差は 0.05% 以下である。

## 期限の既定値の提案

期限の既定値として 100 ms を提案する（仮）。
要件定義 7 章の「期限の初期値」はオーナーが決める項目なので、要件定義は書き換えない。

上限の側の根拠は、応答時間の目安として広く引かれる Nielsen の 3 つの限界である。
0.1 秒は利用者が「即座に反応した」と感じる限界とされる（[Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)、Jakob Nielsen、1993 年）。
期限をこれより長くすると、応答しない拡張機能を待つ間、利用者は遅れを感じる。

下限の側の根拠は、計測した値である。
起動済みの拡張機能の往復と、編集の直後の往復は、間隔を置いた計測で最大 2.1 ms だった。
1 行のバッファを開いた状態からの起動と最初の応答は、最大 2.79 ms だった。
100 ms はどちらに対しても 30 倍以上の余裕がある。

一方で、基本設計 5.2 の状態の表は、未起動の拡張機能の操作が呼ばれたとき、起動と応答が 5.4 の期限の中で終わらなければ失敗するとしている。
起動と最初の応答の時間は、全文の送信に比例して伸び、10 万行で 43〜56 ms、100 万行で 411〜547 ms だった。
1 万行あたり約 4〜6 ms の割合なので、100 ms に収まるのはおよそ 18 万〜24 万行までと推測する（その間の行数は測っていない）。
それより大きいバッファを開いた直後に、未起動の拡張機能のテキストオブジェクトを使うと、最初の 1 回は期限を超えて失敗する見込みである。
2 回目からは、拡張機能が稼働中になっているので期限に収まる。

この失敗への対処として、次の案がある。
どれを採るかは、期限の既定値と合わせてオーナーの裁定を待つ。

- 期限を 100 ms のままにし、大きなバッファでは最初の 1 回が失敗することを受け入れる
- 起動を含む問い合わせだけ、別の長い期限（たとえば 1 秒）を使う。基本設計 5.2 の状態の表の書き換えが要る
- 本体の起動時か、バッファを開いた時点で、起動の契機を待たずに拡張機能を起動しておく。要件定義の FR-14（宣言した契機で初めて起動する）と食い違う

この提案は次の点を確かめていない。

- 計測した拡張機能は、行の空白を数えるだけの軽い処理である。構文の解析などを伴う拡張機能の処理時間は含まない
- イベントループと画面の描画を通していない。キーを押してから画面が変わるまでの時間は、この計測の値より長くなる
- 計測したのはマシン 1 台だけである。他の処理が CPU を多く使っているときと、遅いマシンでの値は測っていない
- 拡張機能の実行ファイルは、繰り返しの起動でページキャッシュに載っていた。エディタを起動した直後の、ディスクから読む起動は測っていない
- 間隔を置いた計測は、20 ms と 200 ms の 2 通りだけである。数秒以上空いた後の往復は測っていない

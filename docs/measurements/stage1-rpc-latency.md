# 段階 1 の検証: 拡張機能への RPC の応答時間

要件定義 8 章の段階 1 は、別のプロセスで動く拡張機能への RPC の応答時間が、キー入力ごとの操作に使える範囲に収まるかを確かめる段階である。
この文書は、その計測の手順、数値、結論と、基本設計 5.4 の期限の既定値の提案を書く（#36）。

## 結論

起動済みの拡張機能への `textObject/resolve` の往復は、3 回の計測のどれでも p50 が 28〜39 µs、p99 が 79〜86 µs、最大が 0.54〜0.98 ms だった。
10 万行のバッファで編集の差分を送った直後の往復も、p99 が 0.31 ms 以下、最大が 2.0 ms 以下だった。
未起動の拡張機能を起動して最初の応答を受け取るまでは、1 行のバッファで最大 2.64 ms、10 万行のバッファ（全文の送信を含む）で 41〜44 ms だった。

この数値から、キー入力ごとの問い合わせを別のプロセスへ送る設計は、このマシンでは応答時間の点で実用になると判断する。
期限の既定値は 100 ms を提案する（仮）。
根拠は「期限の既定値の提案」の節に書く。

## 計測したもの

本体の側は `internal/exthost` の `Host` を使い、拡張機能の側は標準の拡張機能 `cmd/modal-editor-ext-line`（行のテキストオブジェクト `il` と `al`）を子プロセスとして起動した。
イベントループ（`internal/editor`）は端末ライブラリの裁定（#9）を待っていて未実装なので、イベントループと画面の描画は計測に含まない。
`Host.ResolveTextObject` を呼んだ goroutine が応答を受け取るまでの時間を測った。

| 項目 | 測った区間 | 回数 |
|---|---|---|
| 起動から最初の応答まで | 1 行のバッファを開いた未起動の拡張機能へ問い合わせ、子プロセスの起動、`initialize`、`buffer/open` を経て応答が届くまで。回ごとに `Host` を作り直す | 100 |
| 起動済みの往復 | 100 行のバッファで、稼働中の拡張機能への往復。測る前に 1,000 回捨てる | 10,000 |
| 1 万行と 10 万行、行の中の編集 | `Host.ChangeBuffer` で 1 文字の挿入か削除の差分を送り、直後に新しいバージョン番号で問い合わせて応答が届くまで。測る前に 100 回捨てる | 5,000 |
| 1 万行と 10 万行、行を足す編集 | 同じく、1 行の挿入か削除の差分を送り、直後の往復まで。行の数が変わるので、本体の写しと拡張機能の複製で、行の配列の編集位置より後ろを動かす | 5,000 |
| 1 万行と 10 万行の開始 | 大きなバッファを開いた未起動の拡張機能へ問い合わせ、起動、全文の送信、最初の応答まで | 1（各計測で 1 回だけ） |

大きなバッファの 1 行は 40 バイトの ASCII で、10 万行で約 4 MB である。
編集の位置とカーソルはバッファの中央の行に置いた。

p50 と p99 は、測った値を小さい順に並べ、最も近い順位の値（nearest-rank）を取った。

## 環境

| 項目 | 値 |
|---|---|
| 計測した日付 | 2026-11-16（JST の 02:07〜02:08） |
| CPU | AMD Ryzen 9 8945HX（16 コア 32 スレッド、最大 5.06 GHz） |
| メモリ | 29 GiB |
| カーネル | Linux 7.0.0-31-generic |
| Go | go1.27.4 linux/amd64、`GOMAXPROCS=32`、`-race` なし |
| 計測の直前の負荷 | `/proc/loadavg` の 1 分平均が 1.09〜1.12 |

同じマシンで他の作業が重い処理を走らせている可能性があったので、計測を 3 回繰り返し、各回の前後に `/proc/loadavg` を記録した。
3 回とも 1 分平均は 1.09〜1.19 で、32 スレッドに対して低かった。

## 手順

リポジトリの最上位で次を打つ。
計測のテスト（`internal/exthost` の `TestStage1Latency`）は、`cmd/modal-editor-ext-line` を一時ディレクトリへビルドし、宣言ファイル `manifest.json` と一緒に置いてから起動する。
環境変数 `MODAL_EDITOR_LATENCY` が `1` でないときは読み飛ばすので、`make test` では動かない。

```console
$ MODAL_EDITOR_LATENCY=1 go test -run TestStage1Latency -count=1 -v ./internal/exthost
```

`RESULT` で始まる行が各項目の結果である。
3 回の計測は、この命令を 5 秒の間隔で 3 回続けて打った。

### ばらつき

p50 は、2 回目の起動と起動済みの往復を除いて、3 回の差が 2 割以内だった。
2 回目は起動と起動済みの往復の p50 が他の回より 3〜4 割大きかった。
原因は確かめていない。
同じ時間帯に他のプロセスが CPU を使った可能性と、CPU の周波数の変動の可能性が考えられる（推測）。

p99 は、起動から最初の応答まで（1.98〜2.59 ms）と 10 万行の行を足す編集を除いて、3 回の差が 2 割以内だった。
10 万行の行を足す編集の p99 は 0.19〜0.30 ms と幅が大きかった。
この編集は 1 回ごとに 10 万要素の配列の後ろ半分を動かし、大きな割り当てを伴うので、ガベージコレクションに当たるかどうかで値が揺れると推測する（プロファイルは取っていない）。

最大は 1 回だけの外れ値なので、回ごとの差が大きい（10 万行の行の中の編集で 0.30〜2.0 ms）。
最大を期限の根拠に使うときは、この幅を見込む。

## 期限の既定値の提案

期限の既定値として 100 ms を提案する（仮）。

基本設計 5.2 の状態の表は、未起動の拡張機能の操作が呼ばれたとき、起動と応答が 5.4 の期限の中で終わらなければ失敗するとしている。
このため期限は、起動済みの往復だけでなく、起動から最初の応答までを含めて決める必要がある。
計測では、10 万行のバッファを開いた状態からの起動と最初の応答が最大 43.5 ms だった。
100 ms はこの値のおよそ 2 倍で、起動済みの往復の最大（2.0 ms）に対しては 50 倍の余裕がある。

上限の側の根拠は、応答時間の目安として広く引かれる Nielsen の 3 つの限界である。
0.1 秒は利用者が「即座に反応した」と感じる限界とされる（[Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)、Jakob Nielsen、1993 年）。
期限をこれより長くすると、応答しない拡張機能を待つ間、利用者は遅れを感じる。

この提案は次の点を確かめていない。

- 計測した拡張機能は、行の空白を数えるだけの軽い処理である。構文の解析などを伴う拡張機能の処理時間は含まない
- イベントループと画面の描画を通していない。キーを押してから画面が変わるまでの時間は、この計測の値より長くなる
- 計測したのは負荷の低いマシン 1 台だけである。負荷の高いときと、遅いマシンでの値は測っていない
- 拡張機能の実行ファイルは、繰り返しの起動でページキャッシュに載っていた。エディタを起動した直後の、ディスクから読む起動は測っていない

要件定義 7 章の「期限の初期値」はオーナーが決める項目なので、この文書は書き換えない。

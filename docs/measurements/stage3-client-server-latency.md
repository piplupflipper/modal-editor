# 段階 3 の検証: server と client の間の応答時間

要件定義 8 章の段階 3 は、client と server の間のソケットを通っても、日常の編集の応答が 1 つのプロセスの構成と比べて実用の範囲に収まるかを確かめる。
この文書は、その計測の手順、数値、判定を書く（#190）。
判定の基準は要件定義 8.1 にある。

## 結論

画面を格子の差分（変わった行）で送る形で、要件定義 8.1 の基準を判定した。
8.1 は、操作と間隔の組み合わせ（8 通り）ごとの 2 つの基準を、3 回の計測のすべてで満たすことを求める。
**他の作業を止めた静かな状態で測った 3 組目は、基準を満たした。**
他のワーカーのビルドとテストが動いていた可能性のある 1 組目と 2 組目は、満たさなかった。

| 組 | 本体 | マシンの状態 | 遅れの基準（分けた構成の p99 ≦ 1 つのプロセスの構成の p99 + 1 ms） | 最大の基準（分けた構成の最大 ≦ 20 ms） |
|---|---|---|---|---|
| 1 組目 | a110b91（client が描くたびに格子を作り直す） | 他の作業が動いていた可能性がある | 24 のうち 2 つで満たさない（1 回目の `dd` 20 ms で +1.05 ms、2 回目のインサートモードの入力 20 ms で +2.51 ms） | 24 のすべてで満たす（最大 7.92 ms） |
| 2 組目 | c364fb3（client が格子を使い回す） | 同上 | 24 のうち 1 つで満たさない（3 回目の `j` 200 ms で +1.20 ms） | 24 のすべてで満たす（最大 8.93 ms） |
| 3 組目 | 39760ee（2 組目にレビューの推奨を反映したもの。計測のときのコミットは aa291c0） | 他のワーカーを止めた（2026-11-18 のオーナーの裁定。#190 のコメント） | **24 のすべてで満たす**（差は +0.08〜+0.41 ms） | **24 のすべてで満たす**（最大 2.64 ms） |

3 組目の p50 の差（分けた構成 − 1 つのプロセスの構成）は +0.10〜+0.28 ms、p99 の差は +0.08〜+0.41 ms だった。
1.5 ms 以上の外れ値は、3 回 × 16 の組み合わせ × 300 回のうち 2 回だけだった。

1 組目と 2 組目の失敗は、数 ms の外れ値が 1 回の計測の中で 4 回以上出て、p99（300 回のうち大きい方から 4 番目）を押し上げたことによる。
1 組目と 2 組目は回ごとの記録と GC の記録を取っていないので、その外れ値の原因は確かめていない。
オーナーの裁定（#190 のコメント）は実行のトレースなどで確かめることだったが、取ったのは `GODEBUG=gctrace=1` と 1 秒ごとの CPU の記録で、`runtime/trace` は取っていない。
外れ値の原因を、3 組目の後に、判定に使わない別の回（診断の回。「外れ値の原因」の節）で調べた。

- 静かな状態で `GODEBUG=gctrace=1` を付けた回の 1.5 ms 以上の外れ値 4 回は、どれも server と client の GC と時刻が重ならなかった（テストのプロセスの GC は記録していない）。GC の停止（STW）は 511 回の p50 が 0.05 ms、最大が 0.47 ms だった
- 他のプロセスが CPU を使うと増える。`go build -a` を繰り返して負荷を掛けた回では、1.5 ms 以上の外れ値が 247 回（1 つのプロセスの構成で 82 回、分けた構成で 165 回）に増え、遅れの基準を 8 つのうち 7 つで満たさなかった。そのうち GC と時刻が重なったのは 56 回（23%）だけだった
- 残りの外れ値は、他のプロセスのために本体のスレッドが CPU を待った（スケジューラーの待ち）ためと推測する。システムコールの待ちと区別する実行のトレース（`runtime/trace`）は取っていない
- 分けた構成は、1 回のキーで起きるプロセスとスレッドが 1 つのプロセスの構成より多い（client と server の 2 つ）ので、CPU を待つ機会が多く、負荷の下で外れ値が約 2 倍になったと推測する

この結果から、静かな状態では、格子の差分で送る形が 8.1 の基準を満たすと判断する。
負荷の下では、分けた構成の方が外れ値が多い。
8.1 の基準は負荷の条件を定めていないので、負荷の下の値をどう扱うかはオーナーの判断である。

## 計測したもの

本体の実行ファイル 1 つを、次の 2 つの構成で起動した。
どちらも拡張機能なし、利用者の設定なし（`XDG_CONFIG_HOME` などを空のディレクトリにした）である。

| 構成 | 起動のしかた |
|---|---|
| 1 つのプロセスの構成（FR-60） | `modal-editor <ファイル>` を偽の端末の上で起動する。server と編集の client は同じプロセスの中で、チャネル（`protocol.Pipe`）でつながる。画面は格子をそのまま渡す |
| 分けた構成 | `modal-editor -listen <ソケット> <ファイル>` で server だけを起動し（端末なし）、`modal-editor -connect <ソケット>` を偽の端末の上で起動する。2 つのプロセスは Unix ドメインソケットの上の JSON-RPC でつながり、画面は格子の差分（変わった行）で送る |

偽の端末は 80 列 24 行の pty で、`make footprint-check` と同じ作り方（`internal/term/ptytest`）である。
tmux は通さないので、tmux そのものの描画は計測に含まない（要件定義 8.1）。

測った区間は、偽の端末の主の側にキーのバイト列を書く直前から、その入力で変わった画面を読み終えた read の時刻までである。
画面は、本体が端末へ書いた出力を計測の側で解釈して作った文字の格子で判定した（CUP で位置を決め、`ESC [ 2 J` で消し、属性は読み飛ばす）。
終わりの判定は、要件定義 8.1 の「期待するバイト列」の代わりに、次の画面の条件にした（8.1 が「仮」として変えてよいとした点）。
本体は画面の差分だけを書くので、変わった行の文字列が続いたバイト列として出るとは限らないためである。

| 操作 | 準備 | 計測するキー | 終わりの条件 |
|---|---|---|---|
| `j` | なし（1 行目から） | `j` | ステータス行の位置が ` <新しい行>,1 ` になった |
| インサートモードでの 1 文字の入力 | `i` | `x` | ステータス行の位置が ` <行>,<列 + 1> ` になった。60 文字ごとに、計測しない改行を挟む |
| `dd` | なし（1 行目を消し続ける） | `dd`（1 回の書き込み） | 画面の 1 行目が、次の行の中身（`line 000002:` など）で始まった（#215 で既定でタブの行を出すようにした後は、画面の 2 行目を見る。#190 の数値はタブの行の無い本体のもの） |
| `p` | 1 行目で `yy` | `p` | ステータス行の位置が ` <新しい行>,1 ` になった |

ファイルは 10,000 行で、1 行は `line 000001: the quick brown fox jumps over the lazy dog 0123456789` の形（NFR-05 と同じ）である。
組み合わせ（操作、間隔、構成）ごとに本体を起動し直し、元のファイルの写しを開いた。
回ごとに、キーの前に間隔（20 ms か 200 ms）だけ待ち、それまでに届いた出力を読み終えてから書いた。
最初の 20 回を捨て、続く 300 回で p50、p99、最大を求めた。
p99 は、300 個の値を昇順に並べた ⌈300 × 99 / 100⌉ = 297 番目である（段階 1 の計測と同じ nearest-rank）。

要件定義 8.1 の操作のうち、「もう 1 つの編集の client で `yy` した直後に、測る client で `p` を打つ」は、#190 では測っていない。
#190 の server は編集の client を 1 つだけ繋いだためである。
複数の編集の client を繋げるようにした #215 で測った（「もう 1 つの client で yy した直後の p（#215）」の節）。
client をまたいだ使い方（8.1 の 2 つ目の表）は、#215 の結合のテスト（`internal/editor` の `clients_test.go`）と tmux の実物で確かめた（#215 の PR の説明）。

## 手順

worktree の最上位で、計測する本体と計測のテストをビルドしてから、テストを 3 回続けて動かした。
1 組目は a110b91 に計測のテストを足した作業ツリーで、2 組目は c364fb3 で行った。
この 2 つのコミットは、PR を作る前に main（5c68691）へ rebase したので、ブランチの上では 527d58f と 7900b5b になった。
rebase で取り込んだ main の変更は、外部のコマンド、拡張機能の管理、`<leader>` のもので、計測した経路（キーの解読、`j`、`x`、`dd`、`p`、描画）には掛からないと見ている（測り直してはいない）。
3 組目は、aa291c0 に回ごとの記録（下の `MODAL_EDITOR_LATENCY_LOG`）を足した作業ツリーで行った。足したのは計測のテストだけで、本体は aa291c0 と同じである。
aa291c0 は、誤ってコミットした実行ファイルを履歴から消したときに 39760ee に書き換わった。ソースは同じである。
その後、大きさの上限を、断る形から切り詰める形に変えた（PR #200 の再レビューの必須 2）。上限に届かない 80 列 24 行の計測の経路には掛からないので、測り直していない。
計測の間は、この作業のビルドとテストを他に走らせていない。
1 組目と 2 組目の間は、同じマシンで他の作業（別の worktree のビルドとテスト）が動いていた可能性があり、そのため負荷を記録した。

```console
$ CGO_ENABLED=0 go build -o "$DIR/modal-editor" ./cmd/modal-editor
$ go test -c -o "$DIR/cmd.test" ./cmd/modal-editor
$ cd cmd/modal-editor
$ MODAL_EDITOR_LATENCY=1 MODAL_EDITOR_BUILD_DIR="$DIR" "$DIR/cmd.test" -test.run TestStage3Latency -test.count=1 -test.timeout 40m -test.v
```

計測のテストは `cmd/modal-editor/stage3_latency_test.go` の `TestStage3Latency` である。
環境変数 `MODAL_EDITOR_LATENCY` が `1` でないときは飛ばすので、`make test` では動かない。
`MODAL_EDITOR_BUILD_DIR` を指定しなければ、テストが `go build` で本体を作る。
1 回の計測に約 10 分かかる。
`RESULT` で始まる行が組み合わせごとの結果で、`VERDICT` で始まる行が 8.1 の 2 つの基準の判定である。

環境変数 `MODAL_EDITOR_LATENCY_LOG` にディレクトリを渡すと、回ごとの記録を書く（3 組目と診断の回で使った）。
`samples.csv` は組み合わせ、回、キーを書いた時刻（UNIX ナノ秒）、値（ナノ秒）で、`procs.csv` は本体のプロセスを起動した時刻、`<組み合わせ>-server.log` と `-client.log` は本体の標準エラー出力である。
診断の回は、これに `GODEBUG=gctrace=1` を足して、本体の GC の記録を標準エラー出力のファイルに出した。

## 外れ値の原因

1.5 ms 以上の値を外れ値とし、回ごとの記録（`samples.csv`）の時刻を、次の 2 つに照らした。

- 本体の GC: 診断の回の `GODEBUG=gctrace=1` の行。行の `@` の秒（起動からの時間、ミリ秒の 3 桁）に `procs.csv` の起動の時刻を足して壁時計の時刻にし、`clock` の 3 つの時間の和を GC の区間とした。`@` の丸めを見込んで前後 2 ms を重なりとみなした
- マシンの状態: 1 秒ごとの CPU の使用率、実行可能なプロセスの数、CPU を多く使ったプロセスの上位 5 つ（`/proc/stat` と `/proc/<pid>/stat` の差を読む道具。リポジトリには置いていない）

| 回 | 1.5 ms 以上の外れ値 | GC と重なった数 | 外れ値の秒のマシンの状態 |
|---|---|---|---|
| 3 組目（3 回） | 2（`dd` 20 ms の分けた構成で 2.30 ms、`j` 20 ms の分けた構成で 2.64 ms） | 記録していない（gctrace なし） | 使用率 1.3% と 1.8% |
| 診断（静か） | 4（すべて分けた構成） | 0 | 2 回は `cadvisor` が 1 秒に 83% の CPU を使った秒、1 回は 54% の秒。もう 1 回は使用率 1.7% |
| 診断（負荷） | 247（1 つのプロセスの構成で 82、分けた構成で 165） | 56（23%） | 使用率は平均 28.0%、実行可能なプロセスの数は最大 35 |

GC の停止（STW）は、診断（静か）の server と client の 511 回で p50 0.05 ms、最大 0.47 ms で、1.5 ms の外れ値を作る長さではなかった。
診断（負荷）では最大 7.54 ms になったが、GC の区間も CPU を待って延びたと推測する。

ここから、外れ値は GC によるものではなく、他のプロセスが CPU を使っている間に、本体のスレッドが CPU を待ったためと推測する。
実行のトレース（`runtime/trace`）は取っていないので、スケジューラーの待ちとシステムコールの待ち（pty とソケットの読み書き）は区別していない。
テストのプロセス（偽の端末を読む側）の GC も記録していない。

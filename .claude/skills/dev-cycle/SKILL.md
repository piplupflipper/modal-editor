# dev-cycle

基本設計（`docs/basic-design.md`）を満たすまで、実装・テスト・レビュー・マージを繰り返すための手順である。
オーケストレータは分割、指示、検証、マージだけを行い、実装とレビューは Opus のワーカーに委譲する。

## 0. セッションの始め方

新しいセッションのオーケストレータは、最初に次を確かめてから issue を切る。

1. この skill の 4 章と、5 章の直近のセッションの記録を読む
2. `docs/progress.md` の集計と、開いている issue（`gh issue list`）を見る。`裁定要` と `低優先` のラベルの issue を分けて数える
3. `docs/basic-design.md` 10 章と `docs/requirements.md` 7 章の未決の項目を読み、オーナーの裁定が要るものと、実装の中で決めてよいものを分ける
4. main の CI が緑か（`gh run list --branch main --limit 1`）を見る。赤なら、それを直す issue から始める
   - **`docs/progress.md` の「実装とテスト」は、画面から使えることを表さない。** 2026-11-16 は 35 件がそろった後に、ACP にプロンプトを渡す手段が無いこと（#130）と、拡張機能の出力・印・ホバーが画面に出ないこと（#132）が見つかった。要件がそろったら、`make dist` の本体を tmux で起動し、標準の拡張機能（LSP、DAP、MCP、ACP、tree-sitter、スクリプト）をそれぞれ実物で使い通して、基本設計 6 章の「最初の範囲」が画面から使えるかを確かめる
   - 通し確認は読み取り専用のワーカー 1 体に任せる。指示には、配布物の作り方（musl-gcc の置き場所）、実物の入手（gopls、dlv は `go install`、ACP は `opencode acp`、MCP は Claude Code の `--mcp-config` の一時の設定）、画面の取り出し方（`tmux capture-pane -e -N -p`）、結果の表の置き場所、「リポジトリを変えない、issue と PR を作らない」を書く。報告は、項目ごとに「使えた／使えなかった（再現の手順）／確かめられなかった（理由）」と、基本設計の節
   - 使えなかった項目は、オーケストレータが 1 件ずつ issue にし、触るパッケージが重ならない組から並列で直す。直したら、同じワーカーに `SendMessage` で同じ手順をもう一度流させる（文脈が残っているので、前回の手順をそのまま再現できる）。2026-11-16 は 1 回目で 5 項目と設定の書き方の欠け、2 回目で 1 項目が見つかり、3 回目の前にすべて直した
5. 2026-11-18 のセッション 2 の終わりの時点で、要件 43 件はすべて「実装とテスト」になっている（セッション 2 でレジスターとマクロの FR-50〜FR-57 を足した）。開いている issue は、揺れるテスト（#169）と低優先の食い違い（#174）である。次の作業は、未決の項目の裁定、`低優先` の issue、要件定義 8 章の段階 3 以降（未定）の相談のどれかになる。新しい要件を作り出さず、まずオーナーに段階 3 以降の方針を聞く

## 1. 役割

| 役割 | やること | やらないこと |
|---|---|---|
| オーケストレータ | issue の起票、ワーカーの起動、報告の検証、レビュー結果の判定、マージ、この skill の更新 | パッケージの実装 |
| 実装ワーカー | 1 issue を 1 PR にする。worktree で実装し、`make check` を通して PR を作る | 担当外のパッケージの変更、マージ |
| レビューワーカー | PR の差分を、基本設計と要件定義に照らして読み、指摘を返す | コードの変更 |

## 2. 実装ワーカーの手順

### 2.1 準備

- リポジトリは `~/ghq/github.com/piplupflipper/modal-editor`（GitHub の `piplupflipper/modal-editor`）。main の作業ツリーは触らない
- 最初に読むもの: この skill、`README.md`、`docs/requirements.md`、`docs/basic-design.md`、担当 issue（`gh issue view <番号>`）
- worktree を作る: リポジトリで `git fetch origin` の後、`gwq add -b <ブランチ名>` を実行し、`gwq get <ブランチ名>` で得たパスへ `cd` する。パスはリポジトリの外の `~/worktrees/github.com/piplupflipper/modal-editor/<ブランチ名の / を - にしたもの>` になる
- `gwq add -b` は、主リポジトリの作業ツリーの HEAD を基点にする。2 つ目の引数は基点ではなく worktree のパスとして扱われる（2026-11-16 に `gwq add -b <branch> origin/main` と打ち、リポジトリの中に `origin/main` という worktree ができた）。基点を新しくしたいときは、主リポジトリで `git pull --ff-only` してから打つ
- `make hooks` は worktree では打たない。検査は `make check` を手で打つ
- ブランチ名は `<verb>/<issue番号>-<slug>`（例: `feat/10-buffer`）

### 2.2 実装の規約

- 基本設計 2 章の層を守る。土台（`internal/buffer`、`internal/rpc`、`ext`）は他のパッケージを import しない。同じ層どうしも import しない
- 編集の状態は、イベントループの goroutine 1 つだけが触る（基本設計 2.1）。土台のパッケージは並行に呼ばれる前提を置かない。ただし `internal/rpc` は内部で goroutine を使うので `-race` で検証する
- コメントと doc コメントは日本語、エラーメッセージとログは英語でも日本語でもよいが、パッケージ内で揃える（既存の `cmd/modal-editor/main.go` は日本語）
- doc コメントは詳細設計を兼ねる（README）。公開する型と関数には、何を表すか・何を保証するかを書く
- `req: FR-xx` の注釈（基本設計 9 章）は、その要件の**振る舞い**を実装した箇所と、その振る舞いを検証したテストにだけ付ける。型や定数を置いただけ、JSON の往復を試しただけの箇所には付けない（2026-11-16 に ext の型だけで 8 件の FR が「実装とテスト」に見えた）
- 要件の振る舞いの一部だけを実装する PR は、その PR の中で要件定義の ID を分け（要件定義の冒頭の規則。元の ID に実装した振る舞いを残し、残りに新しい ID を振る）、実装した側にだけ注釈を付ける。PR #206 は FR-92 の前半（並びの設定）だけで `req: FR-92` を付け、拡張機能の部品の口が無いまま FR-92 が「実装とテスト」に見えた（#208）。`reqtrace` に「一部」の印を足す案は、印を外し忘れても検査で気づけず、残りの振る舞いが要件定義の上で見えないので採らなかった（#238）
- 注釈を変えたら `make progress` で `docs/progress.md` を生成し直してコミットに含める。`make check` は progress の不一致で落ちるので、`make progress` を先に打つ
- `internal/rpc` のハンドラーを読み取りの goroutine から同期で呼び、その中で書き込みを待つと、双方向の通信で互いに詰まる（2026-11-16 の #11 で発生）。接続の上で処理を書くときは、読み取りを止めない形にする
- 外部ライブラリを足すのは、issue か裁定で決まったものだけにする。cgo は本体で使わない（NFR-02）
- 設計に書かれていない点（フィールド名、境界の扱い、仮の数値）は、実装者が決めて PR 説明の「設計との差分」節に書く。止めて聞かない
- issue の指示と基本設計が食い違うときも、実装を止めずに一方を選び、「設計との差分」に理由を書く。基本設計の改訂が要るなら、その旨を書く（オーケストレータが別 issue にする）
- オーナーの裁定が要る項目（外部ライブラリの選定、要件の解釈を変えるもの）だけは決めない。PR 説明の「未確認事項」に「裁定要」と書き、裁定に依存しない形で実装する
- issue の文面と、オーケストレータの指示文の「触ってよい範囲」が食い違うときは、指示文を優先する。issue が求める機能のために範囲を超える必要があれば、最小限で超え、PR の「設計との差分」に理由を書く（#32）
- 拡張機能の側（`cmd/modal-editor-ext-*`）で時間のかかる処理（言語サーバーやデバッガーの応答待ち、構文の解析）を、ext/server のメッセージを処理する goroutine の上で同期に行わない。ping の応答が遅れ、本体の生存確認の期限切れで強制終了される（#47 のレビューで、2 万行の JSON への入力で ping が 3.25 秒になった）。Async のハンドラーか、Clone した複製を別の goroutine で使う
- 拡張機能が子プロセス（言語サーバー、デバッグアダプター）を起動するときは、拡張機能が SIGKILL で終わっても孤児が残らないようにする（`Setpgid` と `Pdeathsig` の組。#58 のレビューで dlv のデバッグ対象が残った）
- エラーの文言は 2 種類に分ける。プログラムの内部で返すエラー（`internal/rpc` の接続の誤りなど）は英語の小文字始まり（Go の慣習。`errors.New("invalid position")`）。画面に出すことを前提にしたエラー（Ex コマンドの誤り、`:q` の未保存など）は日本語にし、Vim に対応するものがあれば `E37` のようなエラー番号を先頭に付ける。doc コメントとコメントは日本語
- 同じ層のパッケージは、テストからも import しない。同じ層どうしの対応（`internal/input` の ID と `internal/command/target` の表など）を確かめたいときは、上の層（`internal/editor`）の結合のテストに回すか、当面はソースを `go/parser` で読んで照合する（2026-11-16 の #26）

### 2.3 Vim の挙動との突き合わせ

- Vim の挙動を写す実装（モーション、オペレーター、Ex コマンド、カーソルの位置）は、記憶で書かずに手元の Vim（2026-11-16 時点で 9.1）で結果を確かめる。#19 では、表の全行を Vim と突き合わせて `3$` と回数付きの `w` の食い違いが見つかった
- 期待値は Ex モードでない起動（`vim -Nu NONE -n --not-a-term -c '...' -c 'wq! out' in`）で取る。`vim -es` は Ex モードで動くので、`:3,4` が E16 になるなど通常の Vim と結果が違う（#54 で判明）。`-es` の結果で作った表は、Ex コマンドの範囲、`<Esc>` と `<BS>` の後のコマンドラインの扱いで誤る
- 突き合わせのスクリプトで `silent!` を付けると、失敗したコマンドの後の先行入力が捨てられず、マクロが失敗で止まらなくなる（#32）。失敗で止まるかを確かめるケースでは付けない
- 突き合わせの道具の例: ケースを生成する Python と、Vim に流す Vim script の組（PR #26 のレビューで作ったもの）。道具はリポジトリには置かず、PR 説明に方法と件数と食い違いの内訳を書く
- 表示幅のように Vim の関数（`strdisplaywidth()`、`charclass()`）で全文字を引ける性質は、全文字で比べ、表を作る道具をリポジトリに置いて `go generate` で作り直せるようにする（#35、#49）
- 要件が Vim と違う挙動を明文で定めているもの（FR-09 の正規表現は Go の `regexp` の文法、など）は、Vim と違っても正しい。doc コメントに違いを書く

### 2.4 検査

- `make check`（整形、型チェック、リント、テスト、`go mod tidy`、progress の一致）を worktree で通す
- 整形で落ちたら `make fmt` を打つ
- リンターの `exhaustive` は非公開の enum の switch も検査する。`default` を書いても列挙しきらないと落ちる
- テストが出力なしで止まったら、`go test -timeout 30s -run <名前> ./<パッケージ>` で止まったテストを特定する（タイムアウト時に goroutine のダンプが出る）
- 初回の `make lint` は golangci-lint のビルドで数分かかる。フォアグラウンドで待つ

### 2.5 コミットと PR

- コミットメッセージは日本語、件名は `<type>: <要約> (#<issue番号>)`。本文はファイルに書いて `git commit -F <ファイル>` で渡す
- コミット末尾にはオーケストレータが指示した attribution の行を付ける
- `git push -u origin <ブランチ名>` の後、`gh pr create --base main --head <ブランチ名> -t "<件名>" -F <説明ファイル> -a piplupflipper` で PR を作る
- PR 説明は日本語で、「変更内容」「設計との差分」「検査結果」「未確認事項」の節を置き、`Closes #<issue番号>` を 1 行で含める。末尾にオーケストレータが指示した 2 行を付ける
- 作成後に `gh pr view <PR番号> --json body --jq .body` で本文を読み返し、`Closes` が入ったことと、事実と違う文が無いことを確かめる
- 大きな作業は段階ごとに commit し、その都度 push する（中断したときの再開点になる）
- 作業の途中で、オーケストレータから他の PR で決まった取り決めが届くことがある。その PR がまだマージされていなければ、取り決めに依存する部分は後回しにして PR の「未確認事項」に書く。マージ後の rebase で対応する

### 2.6 ワーカーの規則

- Agent ツールで他のエージェントに委譲しない
- **リポジトリのファイルの作成と編集は、Edit ツールと Write ツールで行う。Bash でファイルを書き換えない**（`sed -i`、python のスクリプト、heredoc のリダイレクト）。2026-11-16 の #66 では、2 体のワーカーが Makefile を python の heredoc で書き換える Bash の呼び出しで、結果が返らないまま 1 時間ずつ止まった。Edit ツールに替えた 3 体目は止まらなかった
- 長いコマンド（docker、ビルド、負荷をかけたテスト）には `timeout` を付ける
- 本文はファイルに書いて渡す（Write ツールで書く）
- コミットメッセージ、PR 説明、レビュー本文の一時ファイルは、オーケストレータのセッションの scratchpad（指示に無ければ `/tmp` ではなく worktree の外の任意の場所）に置き、ファイル名は `<issue番号>-` を接頭辞にする。worktree の中に置かない（`git add` で混入する）
- `git checkout -- .`、`git restore .`、引数なしの `git stash`、`git reset --hard` を打たない
- 最終報告は日本語で、PR の URL、変更ファイル数、`make check` の結果、未確認事項を 5 行以内で書く
- レビューの差し戻しは同じ worktree で直し、新しい worktree は作らない。main が進んでいたら `git rebase origin/main` し、`docs/progress.md` の衝突は `make progress` で生成し直して解消し、`git push --force-with-lease` する

## 3. レビューワーカーの手順

- 入力は PR 番号だけにする。オーケストレータの見立ては渡さない（結論に引きずられないため）
- `gh pr diff <番号>` と、関係する設計の節を読む。必要なら PR のブランチを worktree に取り出してテストを動かす（`gwq add <ブランチ名>` は既存ブランチの取り出し）
- 観点: 基本設計と要件定義との食い違い、層の違反、テストが要件を実際に検証しているか、`req:` 注釈がその要件の振る舞いの箇所に付いているか、注釈を付けた ID の文の振る舞いが PR で全部そろっているか（一部だけなら ID を分ける。2.2）、境界値（空のバッファ、最終行、多バイト文字、不正な UTF-8）、並行処理の競合、エラーの握りつぶし、Vim の挙動との対応
- **後段の利用者の目で読む。** オーケストレータは、この PR の上に何が載るか（どのパッケージがどう使うか）を指示に書く。2026-11-16 の Wave 1 では、必須の指摘の多くがこの観点から出た（アンドゥのまとめ、保存位置、取り消しの通知名、Close 後のハンドラー）
- 指摘は手元で実際に入力を流して確かめる。PR のパッケージを scratchpad に写して試すか、PR のブランチを `git worktree add <scratchpad のパス> origin/<ブランチ名>` で取り出す（`gwq add` はブランチを作るので使わない）。並行処理は `go test -race -count=50` で揺さぶる
- 指摘は「必須（マージ前に直す）」「推奨（別 issue でよい）」に分け、`path:line` と、失敗する具体的な入力を付ける
- Vim の挙動が関わる PR は、実装ワーカーの「Vim と一致した」を抜き取りで確かめ、表に無い境界を足して Vim と突き合わせる（2.3）
- 要件が明文で定めていること（FR-09 など）は指摘にしない。要件の解釈が割れると考えたら「裁定要」として書く
- 外部のプロセス（言語サーバー、デバッガー）と話す PR は、手元に実物（gopls、dlv）を入れて 1 回動かす。#58 と #59 の必須の指摘（孤児のプロセス、gopls の整形の結果）は、偽のサーバーのテストでは出ず、実物でだけ出た。`go install` の `GOBIN` は scratchpad にする
- 計測を含む PR は、測り方が測りたいもの（キー入力ごとの応答など）に合っているかを見る。#37 は問い合わせを間を置かずに送っていて、間隔を挟むと p50 が 30 µs から 122〜230 µs になった
- 結果は `gh pr review <番号> --comment -F <ファイル>` で PR に残し、最終報告に必須の指摘の件数と要旨を書く

## 4. オーケストレータの手順

1. 基本設計の未実装部分から issue を切る。同じファイルを触る issue は並列にしない（`docs/progress.md` は例外。後述）
   - issue が FR の振る舞いの一部だけを扱うなら、issue を切る前にオーケストレータが要件定義の ID を分けて新しい ID を採番し（要件定義の冒頭の規則）、issue に扱う ID を書く。並列の 2 つの PR がそれぞれ「次の空き番号」を取ると、同じ ID を振って main で衝突し、`docs/progress.md` で別の要件の注釈が混ざるためである（PR #239 のレビュー。FR-50〜FR-57 を先に採番した PR #164 と同じ形）。ワーカーが PR の中で分ける規則（2.2）は、issue を切った後に一部だけになったと分かった場合のためのもので、そのときも番号はオーケストレータに聞かずに決めてよいが、PR 説明に書く
   - 受入条件に「`req:` 注釈を FR-xx に付ける」と FR を列挙しない。列挙するとワーカーは型だけの箇所にも付ける。「振る舞いを実装・検証した箇所にだけ付ける」と書く
   - 並列に作る土台どうしの契約は、両方の issue に同じ文で書く。2026-11-16 は buffer と ext で編集の座標の基準が、ext/server と exthost で全文に末尾の改行を含めるかが食い違った。いま決まっている契約は次のとおりで、新しい issue には「契約」節としてそのまま写す
     - 編集の座標は逐次の数え方（各編集の位置は、直前の編集までを適用した後のテキストで数える。LSP の didChange と同じ）
     - 行は Vim と同じく数える（`"a\nb\n"` は 2 行）。拡張機能へ送る全文には末尾の改行を含めない
     - 回数は `internal/input` の `Count` と `CountGiven`
     - 拡張機能への問い合わせの失敗は result の `ok` が false
   - issue が求める機能に要る通信のメソッドが `ext/message.go` と基本設計 5.3 の表にあるかを、issue を切る前に確かめる（#24 で `command/execute` が無かった）
   - issue 本文に「この上に何が載るか」を書く。実装ワーカーとレビューワーカーの両方が後段の要求を考えられる
2. 裁定が要る項目は `裁定要` のラベルを付けた issue にまとめ、依存しない issue を先に進める
   - ワーカーやレビューが「裁定要」と書いた項目は、そのままオーナーへ回さず、まず要件定義と基本設計の明文で決まるかを確かめる。決まるならオーケストレータが決めて理由を指示に書く。2026-11-16 は、go-tree-sitter のタグが GitHub に無い件（モジュールプロキシの `.info` の Origin で公式のタグと確かめた）と、yaegi の制限モード（要件定義 3.2 が悪意のある拡張機能を対象外にしている）を、オーケストレータが決めた
   - オーナーへ回す項目は、オーナーが PR を読まずに判断できる形（問い、選択肢ごとの長所と短所、推奨と理由）にする（#43）
   - 裁定を避けられる技術的な代案があれば、そちらを採る。#87 では、glibc を静的にリンクすると LGPL の再リンクの義務が付く（配布の方針はオーナーの裁定）ので、musl（MIT）で静的にリンクする形に替え、裁定はリポジトリ自身のライセンスだけに絞った
   - 裁定待ちの機能でも、裁定に依存しない部分（MCP のツールの中身、ACP のセッションの扱い）は先に作れる。issue に「裁定に依存する部分」と「依存しない部分」を分けて書き、依存する部分は差し込みの口にしておく
3. 実装ワーカーを並列で起動する。指示には issue 番号、ブランチ名、触ってよいディレクトリ、並行するワーカーの担当、attribution の行、一時ファイルの置き場を書き、手順はこの skill を読ませる。指示文の先頭に【報告は必ず日本語で書くこと】を置く。最終報告の形式は 2.6 を指す
4. 報告が来たら（ワーカーの報告の調子は自信の有無を表さないので）、`git diff --stat origin/main...origin/<branch>` で範囲を確かめ、worktree に未コミットの変更が無いか `git -C <worktree> status --short` で見る
5. レビューワーカーを起動する。必須の指摘は実装ワーカーへ `SendMessage` で差し戻す
6. CI（`gh pr checks <番号>`）が緑で、必須の指摘が無ければ `gh pr merge <番号> --merge --delete-branch` でマージする。マージ後に `git log origin/main` で入ったことを確かめる
   - **CI の判定と merge を 1 つのコマンドの `&&` で繋ぐときは、判定のコマンドをパイプに通さない。** `gh pr checks <番号> --watch | tail -1 && gh pr merge …` は、CI が失敗しても `tail` の終了コード 0 で merge まで進む（2026-11-16 の #115 で、失敗した CI のまま merge した）。`gh pr checks <番号> --watch >/dev/null && gh pr merge …` のように、判定のコマンドの終了コードをそのまま使う。表示が要るなら別のコマンドで出す
   - merge の後に、main の CI（`gh run watch <run> --exit-status`）が成功したことを確かめる。PR の CI が揺れるテストで落ちた場合は、手元で `-count` を回して揺れかを確かめ、揺れなら issue にする。揺れでなければ revert の PR を作る
   - **stacked PR（上段の base が下段のブランチ）の下段は、`--delete-branch` を付けずにマージする。** 下段のブランチを消すと、GitHub は上段を main へ付け替えずに CLOSED にした（2026-11-16 の #133 → #134）。手順: 下段を `gh pr merge <下段> --merge` → `gh pr edit <上段> --base main` → 下段のブランチを `git push origin --delete <ブランチ>` で消す → 上段の CI を待ってマージ。閉じられてしまったら、下段の head（`gh pr view <下段> --json headRefOid`）を同じブランチ名で push し直し、`gh pr reopen <上段>` してから付け替える
   - `gh pr checks` が「no checks reported」になるのは、PR が main と衝突していて pull_request の CI が走らないときである。`gh pr view <番号> --json mergeable` を見る。マージの直後は `UNKNOWN` が返るので、数秒おいて読み直す
   - 小さな変更（数十行で、振る舞いを変えない性能の修正など）は、オーケストレータが差分を読んでレビューの代わりにしてよい。その場合も、失敗の経路（途中で失敗したときの巻き戻しなど）を読む。#41（MCP の中継）は、オーケストレータが読んで、標準入力の EOF でソケット全体を閉じると最後の応答が失われる穴を見つけた
   - レビューの「推奨」で、この PR の範囲を超えるもの（他のパッケージの取り決め、設計の改訂）は、差し戻さずに issue にする。差し戻しに入れると PR が膨らみ、並行する PR と衝突する
   - Vim との細かい食い違い（アンドゥ後のカーソルの列など）は、要件定義 1 章が 100% の互換を目指さないとしているので、日常の編集で困るものだけを直す。残りは `低優先` のラベルの issue に 1 本でまとめる（#89）。食い違いを 1 件ずつ issue にすると、#79 → #85 → #86 → #88 のように連鎖して終わらない
7. 後続の PR は main へ rebase し、`make progress` を打ち直す（`docs/progress.md` はほぼ全 PR が触るので、毎回ここで衝突する）。差し戻しは実装したワーカーに `SendMessage` で送る。作業中のワーカーにも `SendMessage` で取り決めを届けられる（次のツールの呼び出しのときに届く）
   - `docs/progress.md` は注釈の行番号を含むので、2 つの PR が衝突なしにマージできても、main で一覧がずれることがある。マージの後に main で `go run ./cmd/reqtrace -check` を打つ
8. ワーカーが止まっていないかを見る。完了の通知が長く来ないときは、ワーカーの transcript（`~/.claude-flt/projects/<プロジェクト>/<セッション>/subagents/agent-<ID>.jsonl`）の更新時刻と、最後の行のツールの呼び出しを見る。30 分以上更新が無く、最後がツールの呼び出しなら止まっている。worktree の `git status` で未コミットの変更を確かめてから `TaskStop` し、同じ worktree で続きをやるワーカーを新しく起動する。指示には、前のワーカーが分かったことと止まった呼び出しの種類を書く（#66）
9. セッションの終わりに、5 章へ反省を書き足し、規則に織り込めるものは 1〜4 章を直す
10. 裁定に依存しないタスクを使い切ったら、新しい作業を作り出さずに止まる。`docs/progress.md` で未着手の要件と、それぞれが待っている裁定の issue をオーナーへ示し、裁定を待つ。issue に書いただけでは返事が来ないことがある（2026-11-16 は #9 と #43 に約 16 時間返事が無かった）。他にすることが無くなった時点で、AskUserQuestion で選択肢（推奨を先頭）として聞くと、その場で返った
11. 裁定が出たら、裁定を issue のコメントに記録して閉じ、要件定義と基本設計へ織り込む issue と、差し込みの口にしておいた部分を差し替える issue を切る。オーナーが「こだわりなし」と答えた項目は、推奨案に決めて理由を記録する
   - 裁定に沿って実装した結果、裁定の前提（選択肢の短所の見積もり）と違う事実が出たら、実装は裁定どおり進めたうえで、実測の事実をオーナーへ 1 回知らせる。#113 では、`RLIMIT_AS` の起動の可否が上限に対して単調でないこと、gopls が 6144 MiB を要することが分かった
